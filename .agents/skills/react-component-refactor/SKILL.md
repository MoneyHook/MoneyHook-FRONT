# React Component Refactor

既存の画面を、表示領域・画面制御・テストの役割が追える構成に整理する。ファイルの行数ではなく、責務の境界を分割の根拠にする。

## 対象と境界を確認する

- 対象ファイル、呼び出し元、公開export、APIフック、model、既存テストを読み、表示と制御の責務を列挙する。テスト検出設定と利用できる検証コマンドも確認する。
- 「テスト配置を変える範囲」と「実装を分割する範囲」は別に扱う。ディレクトリ全体のテスト移動が依頼されても、指定された最初のコンポーネント以外の責務分割まで広げない。
- 配置案はfeatureルートからのツリーで示す。`hooks` をどこの配下に作るかを曖昧にしない。対象範囲に重要な未確定事項がある場合だけ確認する。

## 分割の既定方針

既存の構成とユーザーの指定を優先し、次を出発点にする。

- 画面入口は、取得状態に応じた表示とパネルの組み立てを担当する。既存の入口のimport先・export名・propsを保つ。
- 概要、内訳、推移、取引一覧など、意味のある表示領域ごとにファイルを分け、画面専用のサブディレクトリに置く。
- パネル専用の行、ドーナツ、ツールチップ、表示用関数は同じファイルに残す。すべての小部品を個別ファイルにすることを目標にしない。
- 複数パネルで実際に使う枠やアイコンだけを画面内の共有部品として切り出す。他画面や`shared`への共通化は今回の抽出から自動的に行わない。
- 読み込み・空状態は必要に応じて画面専用の状態表示ファイルにまとめる。既存のエラーUIと再試行の接続は入口に残せる。
- URL同期や画面遷移を含む画面制御は、feature直下の`hooks/use-<screen>-controller.ts`へ分離する。既存APIフックを呼び、取得状態・選択値・用途別の操作関数を返す。パネルは値とコールバックをpropsで受け取る。
- 既存のAPI取得・DTO変換・modelの計算を作り直さない。URLやサーバーデータを別のlocal stateへ複製しない。

例：`src/features/analysis/`を基点に、入口を`components/analysis-categories.tsx`、表示領域を`components/categories/`、制御を`hooks/use-analysis-categories-controller.ts`へ置く。この名称・パネル数は他の画面へ固定しない。

## テスト配置を整理する

- 実装との混在解消が依頼された場合、対象の`components/__tests__/`へ既存テストをまとめることを既定とする。対象コードの近くに置く方針を維持し、他の層のテストまで移動しない。
- 相対import、モックの対象、fixtureやファイル読み取りのパスを点検する。対象外テストの内容は移動に必要な修正に留める。
- 既存の検出パターンで新配置を拾えるなら設定を変更しない。画面の分割に合わせて統合テストまで小部品単位へ分解する必要はない。

## 挙動を保って検証する

- 抽出時はJSX、class、文言、チャート設定、表示件数、無効化状態を保つ。デザイン調整や機能追加は別の依頼として扱う。
- URLのデフォルト・不正値補正・無関係なパラメータ保持・履歴のpush/replace、API取得条件、選択状態、編集画面への遷移と戻り先を保つ。既存の不具合を見つけた場合は、機械的な抽出に紛れ込ませず報告する。
- 既存の統合テストを中心に確認する。抽出した境界にカバレッジ不足があれば、読み込みから成功への遷移、エラーから再試行、空状態、URL連動操作、戻り先の検索条件・hash保持など、該当する観測可能な挙動だけを補う。
- ファイル数、行数、内部関数名の一致だけを検証するテストは追加しない。移動前後のコード比較は、挙動差が混入していないことを確認する補助として使える。
- リポジトリのコマンドで対象テスト、型検査、lint、buildを実行する。テストの引数が実際に絞り込みとして解釈されたか、実行結果の対象と件数を確認する。
- 新規ファイルも含めて差分を見直す。完了時は構成変更、公開インターフェースへの影響、実際の検証結果、警告・未実行項目を簡潔に報告する。
