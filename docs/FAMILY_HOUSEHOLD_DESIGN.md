# 家族の家計記録 — 機能設計

更新日: 2026-09-29。ユーザー確認済みのv1仕様と、v2以降の対象を記載する。実装状況と配備前の確認事項は実装計画書に記載する。テーブル・API・移行・実装順序は [実装計画書](FAMILY_HOUSEHOLD_IMPLEMENTATION_PLAN.md) を参照。

## 1. 採用した要件

- 家族それぞれがログインして共同で記録する。
- 参加・作成できる有効な家族グループは同時に1つ。管理者を含め暫定3人まで。
- 入力時に「個人用 / 家族用」を選ぶ。デフォルトは各ユーザーが設定し、APIに保存して端末間で同期する。未設定時は個人用。登録先を明示したリンクと家族画面の追加操作を設定値より優先し、入力開始後の再取得で登録先を変更しない。
- 自分の取引は個人が原本を所有する。家族用で登録した自分の取引は、自分の記録としても残り、家族に共有される。
- 個人原本を共有した記録は所有者本人だけが編集・削除・共有解除できる。他の家族は管理者を含め閲覧のみ。家族専用の代理記録は家族全員が編集・削除できる。
- 家族の代理入力は家族内だけの記録として保存する。支払者を指定しても、その人の個人データを作成・更新しない。
- 退出時には本人が個人原本を保持し、家族側に退出時点の控えを残す。以後は同期しない。
- 作成者を管理者とし、招待・参加解除・管理者交代を担当させる。参加時は家族の過去分も閲覧可能、退出後は家族へのアクセス不可。
- 大カテゴリは共通、支払方法と独自サブカテゴリは個人用・家族用で分ける。
- 家族用の手入力・一覧・分析を初期版に含める。家族用予算・定期収支・CSVは後段とする。個人用の既存機能は維持する。
- 代理記録を個人へインポートする機能は将来必要だが、v1には含めない。
- 立替・負担割合・精算は扱わない。

## 2. 記録の種類と集計

| 種類                 | 保存先・所有者                         | 個人の集計                               | 家族の集計                |
| -------------------- | -------------------------------------- | ---------------------------------------- | ------------------------- |
| 個人用               | 本人が個人原本を所有                   | 本人に1回計上                            | 対象外                    |
| 家族用・本人の支払い | 本人が個人原本を所有し、家族が共有参照 | 本人に1回計上                            | 共有中は1回計上           |
| 家族用・代理入力     | 家族が独立した記録を所有               | 誰にも自動計上しない                     | 1回計上                   |
| 退出時の控え         | 家族が退出時点の記録を保持             | 控え自体は計上しない。本人には原本が残る | 共有参照の代わりに1回計上 |

例: 自分が払った食費4,800円を家族用で登録すると、自分と家族の両方に4,800円が表示される。相手が払った食費4,800円を代理入力すると、家族にだけ4,800円が表示され、相手の個人集計には入らない。

個人集計への帰属は個人原本の所有者で決める。家族用の支払者ラベルだけで他人の個人データへ計上しない。家族の人物別集計は支払者ラベルを使うため、その人の個人集計と一致するとは限らない。

個人画面は自分が所有する全原本、家族画面は共有参照・代理入力・退出時の控えを表示する。共有状態の確認・共有開始・共有解除は家族の共有管理画面にまとめる。個人一覧には家族切り替え、共有状態フィルタ、共有バッジを追加しない。自分と家族の集計は重なるため、両者を足して総支出とはしない。

収入も同じ構造で、支払者を受取者として扱う。金額は日本円の整数、日付は `YYYY-MM-DD`、IDは文字列。カード購入と引き落としを二重に支出計上せず、家族間の送金も初期版の収入・支出として扱わない。収支差額は口座残高を意味しない。

## 3. 入力と画面

既存の個人用「ホーム・取引・分析・設定」を維持する。ホームに家族画面へのリンク、新規入力に「個人用 / 家族用」の選択、設定に家族設定への入口を置く。家族側は専用のルートを使い、サイドバー・スマホナビゲーションには家族の「ホーム」だけを表示する。家族の取引・分析・設定などの既存ルートは維持し、個人用と同じメニュー項目を並べない。

| URL                                            | 役割                                     |
| ---------------------------------------------- | ---------------------------------------- |
| `/app/family`                                  | 家族の月次収支・最近の取引               |
| `/app/family/transactions`                     | 家族の取引一覧・絞り込み                 |
| `/app/family/analysis`                         | 家族のカテゴリ別・支払い者別分析         |
| `/app/family/sharing`                          | 保存済み個人取引の共有・解除             |
| `/app/family/new`                              | 家族画面からの追加（登録先の選択は維持） |
| `/app/family/transactions/:transactionId/edit` | 本人の共有原本を編集                     |
| `/app/settings/family`                         | 家族・メンバー・招待・入力先の設定       |
| `/app/family/join`                             | 招待からの参加                           |

対象家族・月・家族一覧の絞り込みはURLに保持する。旧個人画面の `scope=household` は家族ルートへ誘導する。キャンセルと原本編集後は遷移元へ戻り、新規保存後は保存先の該当月へ進む。個人編集画面には共有パネルを置かず、共有済み原本の更新・削除時だけ家族側への影響を確認する。家族APIの取得失敗で個人用の保存を止めない。

1. 設定で家族を作成し、一時的な招待コードまたは同じ招待を開くリンクを相手に渡す（招待仕様は第6節）。
2. 各自がデフォルト入力先を設定する。
3. 新規フォームで個人用・家族用を選ぶ。家族用では本人の支払いか代理入力かを区別する。
4. 本人支払いなら「自分の記録にも保存」、代理入力なら「家族にのみ保存・支払者の個人記録には反映されません」と案内する。
5. 家族の一覧で「共有中 / 代理入力 / 退出時の控え」の出所、支払者を確認できるようにする。登録者・最終更新者は詳細で確認する。

新規入力中に個人用と本人の家族用を切り替えても、日付・金額・取引名・サブカテゴリ・支払方法を保持する。本人の記録と代理記録の切り替えでは参照先が異なるため、サブカテゴリ・支払方法を選び直す。1件の入力で選択を変えてもデフォルト設定は更新しない。送信中は変更を無効にし、送信開始時の種類・共有先に保存する。

家族未参加時は個人用だけを利用可能にする。退出・解除後の新規入力は個人用を初期値とし、理由を表示する。入力中の家族用データを無断で個人用へ保存しない。編集時には既存記録の種類を維持し、新規入力のデフォルトを適用しない。

## 4. 記録の操作権限とインポート

個人原本は所有者だけが操作でき、家族専用の代理記録は家族全員が操作できる。

| 記録・操作         | 所有者本人                       | 他の家族（管理者を含む）             |
| ------------------ | -------------------------------- | ------------------------------------ |
| 個人用の非共有原本 | 閲覧・編集・削除・共有開始       | 閲覧・操作不可                       |
| 個人原本の共有記録 | 閲覧・編集・削除・共有解除       | 閲覧のみ                             |
| 家族専用の代理記録 | 家族参加者として閲覧・編集・削除 | 閲覧・編集・削除                     |
| 退出時の控え       | 退出者には家族側へのアクセスなし | 閲覧・訂正・集計からの除外 |

共有記録は家族側にだけある分類・支払方法の項目も含め、所有者以外は変更できない。家族設定の変更や支払方法・独自分類の削除から他人の共有明細が間接的に書き換わらないよう、使用済み項目は無効化して新規候補から外し、既存参照と表示を維持する。管理者による参加解除は、控えを残す所属管理操作として扱う。

- 代理入力の支払者は参加メンバーまたは家族共通を選ぶ。未ログイン人物の追加管理は後段とする。
- 原本の支払者は所有者で固定し、他の人物への所有者変更は許可しない。代理記録の支払者ラベル変更は個人データへ影響しない。
- 本人が原本を編集すると共有表示も更新される。本人が共有中の原本を削除する場合は、個人・家族の両方から外れることを確認し、一括で論理削除・共有終了を行う。退出後の控えは変更しない。
- 個人用から家族用への変更は所有者による共有開始、家族用から個人用への変更は所有者による共有解除とする。共有解除では原本を保持し、家族の集計から外れることを示す。通常の共有解除では退出時の控えは作らない。
- 退出時点の控えは不変とし、家族側の訂正・集計からの除外は最新の訂正内容だけを別に保存する。原本へは伝播しない。
- 本人の登録・共有では個人のサブカテゴリ・支払方法を一度だけ選び、家族側へ名前と支払条件をコピーして保存する。家族共通財布は家族だけの独立記録として保存する。

### v1の重複対処

代理入力と本人の新規入力は別操作なので、同じ支出を本人が再度共有すると家族側で二重計上され得る。日付・金額・支払者の一致を重複候補として示すが、同額の別購入もあるため自動統合しない。

v1では、本人が必要に応じて自分の記録を手入力する。個人用の非共有記録として保存すれば家族には重複しない。家族にも共有する場合は、既存の代理記録を確認のうえ手動で削除する。これはインポートや自動置換ではなく、削除までの間は重複する点を明示する。インポート用の空UI・APIは先に作らない。

### v2以降のインポート要件

支払者本人だけが代理記録を自分の原本へインポートできる。新規原本を作るか、既存原本へ紐づけるかを選び、家族の代理記録は同じ1件の共有参照へ切り替える。個人原本は自動作成しない。インポート後は本人以外の家族には閲覧のみとなる。

既に共有済みの原本との統合、日付・金額等の差分確認、同時操作・再送時の冪等性を設計する。家族の件数・金額が意図せず増えないようにし、元の代理記録IDを維持する。ここは将来要件でありv1の実装・検証対象には含めない。

## 5. 退出・参加解除・再参加

退出・管理者による参加解除は同じ保存処理を使う。

1. 対象者が所有する有効な共有原本から、家族に公開されている項目だけを控えとして確定する。
2. 家族の同じ記録を、共有参照から控えに切り替える。支払者・記録IDの連続性を保ち、重複作成しない。
3. 元の原本と家族の同期を切り、家族から原本への共有読み取り権限を除く。更新権限は共有中から所有者本人だけが持つ。
4. 対象者の所属を終了する。対象者は自分の原本を引き続き閲覧・編集できるが、家族の記録や控えは閲覧できない。

代理入力は元から家族所有なのでそのまま残る。退出者が登録した他メンバーの代理記録も個人用へ移さない。控えには原本の個人用設定をコピーしない。

退出処理と同時編集の順序はAPI側で直列化する。更新版の整合を確認して単一トランザクションで完了し、途中失敗で控えだけ増えたり権限だけ残ったりしないようにする。再試行でも控えを重複生成しない。処理前後で家族の月次合計と本人の月次合計が変わらないことを受け入れ条件にする。

再参加時に過去の控えを自動で原本へ再接続しない。同じ原本を再共有する場合は、既存の控えとの重複を検出して明示的に切り替える操作が必要。初期版ではその操作を提供せず、既存控えに対応する原本の再共有を拒否する。

管理者は1名とし、退出前に参加済みメンバーへ管理者を交代する。最後の1人が終了する場合は家族をアーカイブする。アーカイブ時も有効な共有参照を控えへ切り替え、原本との同期を切る。アーカイブは閲覧専用、招待・入力・更新を停止する。アーカイブ閲覧者と有効な所属枠は分け、終了済み家族が次の家族への参加を妨げないようにする。

アカウントそのものの退会は家族からの退出と区別する。退会機能を提供する前に、控えに残す氏名、保存期間、匿名化・完全削除の仕様を定める。

## 6. 招待仕様

家族を作成すると作成者1人が管理者として参加し、その時点から家族用を利用できる。管理者が招待コードを発行し、相手がログイン後に入力して家族名・招待者・共有範囲を確認し、「参加する」を押す方式とする。同じ招待を開くリンクもコピーでき、コードの手入力を省けるようにする。アプリから外部へ自動送信せず、管理者がLINE等で渡す。

招待は有効期限24時間のコードとリンクを併用する。管理者の追加承認は不要とする。

| 項目           | 仕様                                                                                                              |
| -------------- | ----------------------------------------------------------------------------------------------------------------- |
| 発行権限       | 管理者のみ。残り人数枠がある場合に発行可能                                                                        |
| コード         | 推測困難なランダム英数字10文字。紛らわしい文字を除き、5文字ずつ区切って表示。大文字小文字・区切りは入力時に正規化 |
| 有効期限       | 発行から24時間。画面に期限を表示                                                                                  |
| 利用回数       | 1コードにつき1人・1回のみ。2人を招待する場合は別々に発行                                                          |
| 有効な招待数   | 残り人数枠まで。管理者1人なら最大2件。発行処理も同時実行を制御する                                                |
| 取消・再発行   | 管理者が取消可能。置き換えて再発行した招待の旧コード・旧リンクは無効                                              |
| 参加確定       | ログインした受取人が共有範囲を確認して承諾。管理者の追加承認はv1では設けない                                      |
| 共有範囲の説明 | 過去の家族記録も閲覧できること、個人原本の共有記録は閲覧のみ、代理記録は共同編集できることを参加前に示す          |

コードとリンクは同じ招待ID・失効状態に紐づける。リンクには別の十分長いランダムトークンを用い、コードからリンクのトークンを導出しない。どちらで参加しても両方を使用済みにする。GETやリンクのプレビューでは招待を消費せず、参加の確定操作だけで消費する。

コードの照合・リンクの解決は認証後に行う。未認証で開いた場合はログイン後に安全な参加画面へ戻す。照合前に家族やメンバーの情報を公開せず、照合成功後も承諾前は家族名・招待者・共有条件など必要最小限だけを表示する。URLやコードを第三者へ転送すると、その人も参加できる方式であることを発行時に説明する。

サーバーにはコード・トークンの平文を保存せず、照合用ハッシュを保持する。コード生成は暗号学的乱数を使い、有効コードの衝突を防ぐ。アカウント・送信元単位の試行回数制限を設ける。コード・トークンをログや分析イベントに残さず、参加画面からの外部送信を避ける。

参加確定時に、招待の有効期限・未使用・未取消、家族の有効状態、発行者の管理権限、参加者の所属、最大3人を再検証し、所属追加と招待消費を一括で行う。自分自身の招待承諾、他家族へ所属中の参加、既存メンバーの二重参加は拒否する。既存メンバーの重複操作で人数枠や未使用招待を消費しない。

招待状態は有効・使用済み・期限切れ・取消済みとし、管理者は一覧で状態を確認できる。未承諾の招待はメンバー数には数えない。管理者交代・家族アーカイブでは旧管理者が発行した未使用招待を失効させる。満員・期限切れ・取消時は参加させず、案内を表示する。再送でも所属は重複作成しない。

個人原本と共有記録の操作制限は管理者にも適用する。代理入力・控えの家族権限が個人原本への変更権限になることはない。画面だけでなく、APIの読み取り・編集・削除・共有解除・集計すべてで検証する。

## 7. データとAPIの方針

以下は業務上の論理モデル。物理テーブルとHTTP契約は実装計画書とOpenAPIを参照。

| 概念                 | 責務                                                                                               |
| -------------------- | -------------------------------------------------------------------------------------------------- |
| 個人原本             | 所有ユーザー、金額・日付等、個人側の支払方法・分類、更新版、削除状態                               |
| 家族                 | 名前、管理者、状態                                                                                 |
| 家族所属             | ユーザー、権限、参加・退出状態。人物表示の参照を維持する                                           |
| 家族記録             | 家族ID、種類（共有参照 / 代理入力 / 退出時の控え）、支払者、登録者、家族側の支払方法・分類、更新版 |
| 共有参照             | 個人原本への有効な参照。同一家族・同一原本への有効参照は1つ                                        |
| 代理入力・控えの内容 | 家族所有の金額・日付等。原本の読み取りに依存せず集計可能                                           |
| 招待                 | コード・リンクトークンのハッシュ、発行者、有効期限、消費・取消状態                                 |

所有者・登録者・更新者は認証情報と許可された操作からAPIが確定する。自由な所有者ID指定や記録種類の変更を許さない。共有開始・解除・退出は専用操作として権限、更新版、参照整合性を検証する。家族側APIを経由しても所有者以外から共有原本を変更できない。

共有参照の金額等は原本を正本として取得する。家族側の金額を別の更新先として持たず、退出時にだけ固定する。更新競合は検出して入力内容を残し、再取得を案内する。作成・招待承諾・退出等には冪等性を持たせる。

個人集計は原本、家族集計は各家族記録の種類に応じた正本を使う。一覧・詳細・カテゴリ集計・人物別集計で同じ定義を使う。個人予算の対象は本人原本とし、共有設定変更だけで本人の支出額が変わらないようにする。

家族と個人で支払方法・独自分類が分かれるため、参照IDを使い回さない。本人の家族用新規登録・保存済み原本の共有開始時に、選択した個人項目から家族項目を自動作成・再利用する。退出時は家族側の表示名・参照を保持する。

- サブカテゴリは親カテゴリと名前、支払方法は名前・種別・締め日・支払日の一致で照合する。個人APIで未設定・0の締め日を31日として扱う既存仕様を引き継ぐ。
- 有効な一致項目を再利用し、既存の同一項目が複数あれば最も古いIDを使う。無効化済み項目は復活させず、新規作成する。
- 取引保存と項目の解決は同じDBトランザクションで実行する。家族単位のロックで同時作成の重複を防ぐ。
- 共有中の原本のサブカテゴリ・支払方法の選択を変更した場合は、変更した項目だけ家族側へ反映する。支払方法を解除した場合も反映する。
- 個人設定の名前・支払条件の変更だけで過去の家族記録を更新しない。既存記録への一括補完も行わず、金額だけの編集でも家族側の分類を維持する。
- 家族用の追加選択欄は設けない。選択した名前・支払条件を家族に共有し、未登録項目を自動追加することを入力・共有画面に示す。

## 8. フロントエンドと導入

確認済みの既存実装はユーザー単位で取引・支払方法・予算等を扱い、家族共有や代理記録の概念はない。参照した箇所は `src/app/router/router.tsx`、取引フォーム・mutation・永続キャッシュ、`contracts/openapi.yaml`、Go APIの `app/db/migration/schema.go` と `app/store_postgres/transaction_v1.go`。PRODUCT.mdのプレースホルダー・予算に関する記述にはコードとの相違があるため、実装を基準とした。

- 既存の個人取引は本人所有の非共有原本として維持する。個人記録を自動公開しない。
- 共有・代理入力・控えの契約をOpenAPIへ定義し、Orvalから生成する。生成コードは直接編集しない。
- 閲覧対象と絞り込みはURL Search Params、入力先は設定から初期化するフォーム状態とする。
- TanStack Query・参照キャッシュ・デフォルト支払方法はユーザーと閲覧対象で分離する。入力先デフォルトはユーザー単位でAPI保存する。
- 家族の閲覧レスポンスは初期版ではlocalStorageへ永続化しない。本人原本の個人用キャッシュと、家族の閲覧キャッシュを分離する。
- 家族切り替え・権限喪失時の古いリクエスト結果やキャッシュの再表示を防止する。退出時は家族キャッシュを破棄し、個人原本を再取得する。
- 共有更新は原本・家族記録・個人集計・家族集計の関係する月を無効化する。別端末の更新はフォーカス復帰・画面表示・手動更新で取得する。初期版にリアルタイム通信を含めない。
- feature同士を直接importせず、pageで家族機能と既存取引機能を合成する。

導入はAPIの所有・共有境界、本人による共有登録、代理入力とその共同編集、退出時の控え、v1の重複対処の順で進め、初期リリース前に一連の操作を完成させる。Go APIリポジトリも実装対象とし、migrationをAPI配備前に実行する。

## 9. 検証と対象外

自動テストはUIを介さない契約を対象にし、画面操作は手動確認する。

- 家族に参加しても非共有の原本・個人設定が見えない。
- 代理入力の作成・編集・削除・支払者変更で、誰の個人データも変わらない。
- 管理者を含め所有者以外は共有原本・共有参照の編集・削除・共有解除をAPIから実行できない。
- 代理記録は家族全員が編集・削除できる。v1に個人原本へのインポート経路は存在しない。
- 招待リンクの閲覧では消費せず、確定操作でのみ1回消費する。取消・期限切れ・管理者交代後の招待は承諾できず、コードとリンクは連動して失効する。
- 退出前後で本人・家族の過去合計が維持され、退出後の個人編集と家族側訂正が相互に伝播しない。
- 同時編集と退出、再参加での再共有を含め、アクセス権限と重複防止が維持される。
- 同時招待承諾でも所属家族数と最大3人の制約を超えない。
- 共有開始・解除だけでは本人原本の件数・合計が変わらない。
- 月をまたぐ変更で旧月・新月の個人と家族の集計が更新される。
- 移行前後で既存個人取引の件数・月次合計・関連参照が一致する。

立替・精算、複数家族への同時所属、家族内の一部メンバーだけへの共有、メンバー単位で設定する閲覧専用ロール、代理記録の個人へのインポート、通知・チャット、家族用予算・定期収支・CSVは初期版の対象外とする。
